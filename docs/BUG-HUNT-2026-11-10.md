## Fix first: two regressions from this week

### 1. `S.placed` now holds the wrong thing

`skills.js:490` creates `S.placed = []`, the list of portable tables, furnaces and chests the bot has set down. PR #199
added `S.placed = PL` at `plan.js:872`, where `PL` is the placed-block log from `brain/placed.js`. That object has `at`,
`count`, `byWho`, `near`, `save` and `dispose`. It has no `push` and cannot be looped over.

- `S.placeWork` (`skills.js:491`) places the block and then calls `S.placed.push`, which throws. The block is already in the world.
- `S.ensureTable` and `S.ensureFurnace` pass that error up, so the first craft or smelt at a new spot fails. The retry finds the table nearby and works, which hides the bug.
- `S.reclaim` (`skills.js:497`) throws on its `for...of` and all three callers swallow it. No table or furnace is ever picked up again.
- The `place_chest` skill (`think.js:422`) throws before `mem.setChest`, so the chest stands in the world and the bot forgets it.

Fix: rename the new property, for example `S.placedLog = PL`. Only these five lines read `S.placed`. A mock test that
calls `placeWork` and then `reclaim` would have caught it.

### 2. The forced-look fix bypasses the bot's memory of its own blocks

`plan.js:1227-1236` wraps `bot.placeBlock` and appends every placement to `st.placed`. PR #197 changed `S.placeAgainst`
(`skills.js:450`) and the nav pillar (`reach.js:539`) to call `bot._placeBlockWithOptions` directly. In mineflayer
`placeBlock` calls that function through a local name, so the wrapper never sees the new calls.

Four readers of `st.placed` now miss most of what the bot places:

- scaffold tidy, which takes down plain filler after 10 minutes (`plan.js:1241`)
- the too-close torch tidy (`plan.js:1269`)
- the bot's own chests near home (`plan.js:1095`)
- the recently placed crafting table (`site.js:201`)

Still open after #208. Since #208 makes plain `bot.placeBlock` forced for everyone, the two direct calls could also
simply go back to `bot.placeBlock`, which the wrapper sees.

The forced look was the call shape recommended in the insights doc, and that review did not see this wrapper. Fix: fill
`st.placed` from mineflayer's `blockPlaced` event, which fires for both entry points and only after the server confirms.
`brain/placed.js` already listens to it, so the cleaner end state is one log with the tidy code reading it.

## Hands and inventory: why the held item changes under a job

The logs call this inventory drift and treat it as the server and the bot disagreeing. The code suggests most of it is
the bot's own layers fighting over one hand. Each fix so far added another resync, which is one more actor clicking.

### 3. The fixed hotbar and mineflayer's equip work against each other

Mineflayer's `equip(item, 'hand')` only selects a slot when the item is already in the hotbar. For an item in the bag it
uses the first empty hotbar slot. When the hotbar is full it overwrites slot `nextQuickBarSlot`, a counter that starts
at 0 and steps by one on every such equip (`simple_inventory.js:117-125`). It then selects that slot.

The fixed layout from PR #179 keeps eight slots full. Once slot 9 holds anything, each equip from the bag pushes out the
sword, then the pickaxe, then the axe, and so on. The sorter (`skills.js:824-841`) runs every 30 s and swaps the layout
items back with number-key clicks.

The sorter checks its guards once, before the first swap, and it does not skip the selected slot. So when a job equips
saplings, planks or a bed from the bag and acts more than a moment later, the sorter can put the sword back into the
hand in between. Mineflayer knows the hand changed. The job does not look again.

The guards that exist cover `S.placeAgainst` (2.5 s), the nav pillar and the site pillar (4 s each), an open window and
a dig in progress. Tree farm planting and pillaring, farm replanting, the build engine and the gap between two digs are
not covered. Nine call sites also use `bot.unequip('hand')`, which shift-clicks the held tool into the bag and gives the
sorter more to undo.

Fix, in one place: treat slot 9 as the only scratch slot. Equip from the bag always goes to slot 9. The sorter never
touches the selected slot. "Empty hand" means selecting an empty slot, not moving a tool.

### 4. The resync click is not harmless

Four places ask the server for a fresh inventory by sending a left click on slot -999 with an impossible state id
(`skills.js:600,789,843`, `reach.js:580`). A vanilla server runs a click even when the state id is wrong, and only then
sends the full inventory. A left click outside the window drops the stack on the cursor.

The cursor is loaded between the two clicks of any item move. For moves inside the bag those clicks are microseconds
apart. For the 2x2 crafting grid they are a server round trip apart, many times per craft, and `bot.currentWindow` is
null the whole time because the player inventory is not a "window".

- The 12 s timer skips when a click happened in the last 3 s, but that stamp only sees `bot.clickWindow`. Mineflayer's own `equip`, `putAway` and chest transfers call an inner function and are not stamped.
- The equip wrapper sends the click whenever the last resync is older than 4 s and no window is open. Any eater or reflex that equips during a 2x2 craft triggers it.

Mineflayer 4.39 already has the safe version: `bot._syncWindow(bot.inventory)` sends the end of a drag that never
started, which does nothing on the server and returns the same full resend. Its craft and book code use it.

The code path is certain; how often it fires is not measured. The server behaviour is from memory of the vanilla click
handler and should be confirmed with one trial-server run: put a stack on the cursor, send the click, look for an item
on the ground.

### 5. Nothing owns the hands

`brain/reflexes.js` has a lease for `hands`. Only two places ask it: the combat reflex's `holdSlot` and the hotbar
sorter. Everything else equips at will:

| Actor | Where | When it fires |
| --- | --- | --- |
| Auto-eat plugin | `brain/plugins/index.js:31` | Hunger threshold, any time |
| Safety eat | `brain/safety/runtime.js:352-358` | Low health |
| Combat eat and sword | `brain/combat/reflex.js:244,288` | Mob in range |
| `S.eat` | `skills.js:691` | Planner step |
| Farm eat | `routines/farm.js:26` | During farm work |
| Hotbar sorter | `skills.js:841` | Every 30 s |
| Resync | `skills.js:791` and the equip wrapper | Every 12 s and before equips |

The berry bush planted on a birch spot and the pillar with a sword are both what two of these interleaving looks like.
A lease that every equip, click and consume has to take, with the reflexes allowed to pre-empt, removes the class. It is
the BodyLease from the insights doc applied to the hand first.

To tell contention from real desync in a day: on every full inventory resend, compare the bot's picture before and
after and log how many slots changed and who clicked last. If the count is nearly always zero, the server was never the
problem.

## Climbing and planning

### 6. `L.up` stops one block short and calls it done

A shaft's `entry` is the cell the bot stood in when it started digging. `L.dig` removes the block under it and hangs the
first ladder one below (`ladder.js:104-112`). So the entry cell is air with no floor, directly above the top ladder.

`L.up` sends the pathfinder to `GoalBlock(entry)` (`ladder.js:133`). Three tolerances then stack up:

1. The pathfinder counts a node as reached when the feet are within one block of it vertically. That is true the moment the bot enters the top ladder cell.
2. It reports the goal reached when the cell above the feet matches the goal. Same moment.
3. `L.up` accepts "within 2 blocks of the entry" as success (`ladder.js:134`).

The keys are released with the bot on the top ladder, and a bot that is not climbing slides down. The hand-climb
fallback has the same end: it clears the controls as soon as the feet pass `entry.y - 0.1`, still over the open column.

When the next step starts with a walk, the pathfinder climbs out sideways and nobody notices. When the next step fails
fast, the bot slides to the bottom, the planner sees it is deep underground again, and sends it back up. That is the
ladder bobbing pattern.

PR #194 found the same root in the pathfinder (a path may rise from a rung into the empty cell above it) and removed that
move. It does not change `L.up`, whose goal is still that empty cell. Lab run on 1a11f42, `shaft(76)` fixture, start at
the bottom:

| Goal | Navigator says | Position at return | 5 s later |
| --- | --- | --- | --- |
| Entry cell in the column, `(5, 76, 0)`, as `L.up` uses | ok | y 75.92, not on the ground | y 64, the bottom of the shaft |
| Ledge cell beside it, `(5, 76, 1)` | ok | y 76, on the ground | y 76, on the ground |

In the first row the bot is 0.11 blocks from the entry, so `L.up` returns true, and then it slides the whole shaft. To
reproduce: a ladder lab scenario with `build: s => shaft(s, 76)`, `start: [X + .5, 64, 2.5]`, `goal: [X, 76, Z]`, then
100 more ticks with no controls.

Fix: aim at a floor cell beside the entry and count success only when the bot is on the ground at `entry.y` or above.

### 7. Loops that nobody sees

- The planner's loop check needs the last four picks to be the same step with the same bag (`goals.js:245`). A, B, A, B never trips it.
- A step that returns success has its cooldown cut to 1 s (`goals.js:265`). A step that "succeeds" without changing anything is eligible again at once.
- Steps in the `SURFACE` set pay for a climb to daylight before their own `run` checks whether they can do anything.
- `iron-smelt` fires at 3 raw iron (`plan.js:238`) and is a surface step, so three ore can pull the bot up the whole shaft.
- The idle detector stays quiet when the step name changed inside its window (`detectors.js`, "the autopilot went from one step to another: it is deciding things"). An A, B loop changes the step name constantly.
- The other detectors need a small area. A loop that includes a shaft trip covers too much ground for `oscillating` and for `ladder_bobbing`.

Together these make a class of stall that only a person watching can catch. One detector closes it: over 10 minutes,
count step changes and compare the bag, the placed and dug counts and the distance from the start. Many step changes
with nothing gained is the flag.

## Rules the code cannot keep yet

### 8. Minimum tool tier has no implementation

The rule is the lowest tier that does the job. Every selector picks the fastest tool, which is the highest tier in the bag:

- `autopilot/skills.js:270` (`S.equipFor`, lowest dig time)
- `nav/reach.js:429` and the pathfinder's own dig moves (`bestHarvestTool`)
- `excavation/tools.js:11`, `mining/tools.js:30`, `build/engine.js:67`, `excavate.js:81`
- `pilot/manual.js:126-130`, `routines/farm.js:183`
- `safety/entomb.js:8` lists picks highest first
- the hotbar layout sorts by tier descending, so the best pickaxe sits in slot 2 (`skills.js:818`)

The `tool_tier` detector can flag this but no code can obey it. One `pickTool(block)` that returns the lowest tier whose
tool still drops the block, used by all of these and handed to the pathfinder, is the fix. It belongs in the single
motor layer.

### 9. `digDown` can drop the bot into a cave

`reach.js:599` refuses to dig only when the second block down is a hazard, or is air with lava, a hazard or unloaded
world right under it. Air under air passes. The bot digs its floor and falls however deep the cave is. `L.dig` in
`ladder.js:102` has the right check for the same situation and stops with "open below".

### 10. Two layers disagree on what "arrived" means

`navigator.js:266` treats a goal as met when the feet cell, the cell above or the cell below matches. `S.goto` then
requires the exact feet cell (`skills.js:186`) and returns "nopath" otherwise. A goal one block above or below the bot
comes back at once as a failure without a step taken. Callers read that as unreachable and retry or escalate to digging.
Pick one definition and put it in one function.

### 11. The climb-out fallback escalates

`mining.js:239` says the pathfinder runs "without escalation only if the jump does not land". The call on line 245
passes `{ dig: false, ms: 12000 }`, and `escalate` defaults to true in `S.goto`. A missed jump on the stairs can
therefore end in pillars and dug walls.

### 12. Thunder is not daytime

Nothing reads `bot.thunderState`. `S.isNight` is a clock check, so a thunderstorm at noon counts as a safe day although
hostile mobs spawn on the surface and a bed works. `brain/routines/sleep.js` has no storm case either. The fix is one
predicate, `darkOutside()`, used wherever `isNight` is used for safety.

### 13. Five pillar copies kept the slow look

Fixed while this was being written: PR #208 replaces `bot.placeBlock` in `join.js` with a forced-look version, which
covers every caller below. What follows is the state at 701cf84, kept for the record.

PR #197 fixed `nav/reach.js` and `S.placeAgainst`. These still call plain `bot.placeBlock` at the top of a jump:
`treefarm/engine.js:327`, `excavation/pillar.js:28`, `build/pillar.js:42`, `autopilot/think.js:394`,
`autopilot/site.js:80`. The tree farm copy also still waits for a full block of height before it places, which is the
late end of the window. Deleting them in favour of one pillar is already item 2 in the insights doc.

## Smaller items

### 14. The placed-block log credits players with natural changes

`brain/placed.js:62-69` logs any change from a soft block to a solid one within 6 blocks of a player who swung an arm in
the last 0.7 s. Water freezing to ice (winter in Serene Seasons), a sapling growing into logs and leaves, and gravel or
sand landing all match if someone is working nearby. `NOT_BUILDS` excludes `frosted_ice` but not `ice`. Blocks credited
to a non-bot player count as established for good, so the bots will refuse to dig them. Requiring the new block to be
something a player can hold and place, and skipping leaves, logs above a sapling spot and falling blocks, removes most
of it.

### 15. Shared files between the two bots

- `ladder.js:18` writes the shaft and storage-room registry to `registry.json.tmp` and renames it. Both bots use the same temp name and both read, change and write the whole file with no lock. Two saves close together can lose one bot's shaft or leave a half-written temp file renamed into place.
- `plan.js:28`: `othersAsleep()` is true when no other bot has a fresh mark, because `every` on an empty list is true. With the other bot offline, or after a torn read of `bots-sleep.json`, this bot believes everyone else is asleep.

A per-bot temp name plus a re-read just before the write fixes the first. Requiring at least one fresh mark fixes the second.
